## 2. 計測方法

- 1 試行では新しい sbt JVM を 1 つ起動し、`clean → compile → nativeLink → nativeLink → 1行変更(eval) → nativeLink` を順に実行する。
- 時間は `-Dsbt.task.timings=true` が出すコマンドごとの `Total time: N ms` を使う(sbt の起動時間は含まない)。このプロパティは公式ドキュメントでは確認しておらず、実際に出力されることで確認した。
- 段階ごとの内訳は Scala Native の `Logger.time` の出力を使う。info レベルで出ることは tools のソースで確認した。
- 時間帯によるブレを均すため、条件を巡回させながら 3 周した(base, A, …, F を1周ずつ)。
- 条件ごとに `git worktree` で別ブランチ(`sn-exp/<条件>`)を作り、1 条件だけを変えた。変更内容は `results/condition-diffs.txt` にある。
- 用語: link1 = clean 後最初の nativeLink、link2 = 何も変えずに 2 回目の nativeLink、link3 = 1行変更後の nativeLink(scalac の再コンパイルを含む)

### 増分コンパイルの中身(C, debug ログ)

1行変更後の nativeLink では、LLVM IR ファイル 73 個のうち **再利用されたのは 7 個だけ**(`skiping generation` のログが 7 件)だった。残りの 66 個は再生成と clang での再コンパイルが行われた(`.ll` と `.ll.o` の mtime で確認)。

## 4. 結論

**最も効いた条件**
1. **到達するコードの量を減らすこと(E1)**: link1 が 0.67 倍、link3 が 0.53 倍になった。ただし効いたのはコードの量で、依存の宣言の有無は関係なかった(E1 と E2 の差はノイズの範囲)。Scala Native は到達するコードだけをリンクするので、使っていない依存は時間に影響しない。
2. **0.5.12 での `withMultithreading(false)`(F)**: C と比べて link1 が 0.74 倍、link3 が 0.66 倍になった。既定値の `detect` では、スレッドを使っていないと検出したあとにもう一度リンクする(`Linking (multithreadingEnabled=false)` が約 1.6 s)。F ではこの再リンクがなくなった。
3. **`withOptimize(false)`(A)**: link1 が 0.78 倍、link3 が 0.69 倍になった。Optimizing 段階(約 3.5 s)がまるごとなくなった。その代わり、Generating と Compiling はやや増えた。

**効かなかった条件**
- **mold(B)**: 0.97〜0.99 倍でノイズの範囲だった。最終リンクにかかる時間は 0.5.12 の計測で約 150 ms しかない。
- **増分コンパイル(D1, D2)**: 0.4.17 で有効にしても 0.95〜0.97 倍だった。0.5.12 では無効にしたほうが速かった(link3 が C の 0.88 倍)。1行変更でも IR の 9 割(66/73)が作り直されるため、再利用がほとんど起きていない。
- **0.5.12 への更新(C)**: link1 が 1.30 倍、link3 が 1.08 倍で、かえって遅くなった。主な原因は、マルチスレッド検出による再リンクと、Generating intermediate code が約 2.6 倍に増えたこと。

## 5. 推奨する設定変更(開発時の debug ビルド向け)

- **0.4.17 のまま使う場合**: 開発時だけ `nativeConfig ~= (_.withOptimize(false))` を設定する。clean 後のリンクが 12.2 → 9.5 s、1行変更後が 12.0 → 8.3 s になった。
- **0.5 系に上げる場合**: スレッドを使わないアプリなら `nativeConfig ~= (_.withMultithreading(false))` を併せて設定する。C と比べて clean 後が 15.9 → 11.7 s、1行変更後が 13.0 → 8.6 s になった。なお 0.5.12 のソースのコメントには、この設定は CI でテストされておらず、`Future` を使うコードは実行時に問題が起きうる、と書かれている。
- **入れなくてよいもの**: mold、増分コンパイルの手動有効化。
- **設計の指針**: ビルド時間は、到達するコードの量にほぼ比例していた。circe-generic のような導出系ライブラリでコード量が増えると、ビルドが遅くなる。

## 6. 確認できなかった項目

- 「増分コンパイルが 0.4.9 で実験的に導入された」という前提: 0.4.17 に API があることは確認したが、0.4.9 で導入されたかどうかは未確認。
- 1行変更で 66/73 個の IR ファイルが変わる理由: 未確認。
- 0.5.12 で Generating intermediate code が 0.4.17 の約 2.6 倍かかる理由: 未確認。
- 0.5.12 で増分コンパイルを有効にすると遅くなる理由と、別の変更パターン(たとえば大きなプロジェクトの末端ファイルの変更)でも同じ傾向になるか: 未確認。
- A + F のように条件を組み合わせたときの効果: 計測していない。
- `withOptimize(false)` と `withMultithreading(false)` が、生成されたバイナリの実行性能に与える影響: 計測していない。
- 温まった sbt シェル(JIT が効いた JVM)で計測した場合の差: 計測していない。今回はすべて新しい JVM で計測した。
- CPU 使用率のうち、JVM の JIT や GC が使った分と、ビルドの実処理が使った分の内訳: 未確認。
- 0.4.17 の最終リンク単体の時間: ログに出ないため未計測。Total から各段階を引いた残り(約 0.3 s)から推定しただけ。
- `-Dsbt.task.timings` の公式ドキュメント上の記述: 未確認(実際に出力されることで確認した)。
